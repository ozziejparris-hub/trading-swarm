## Blocking question 1 — does widening recreate the hydrate trap?

### (a) Actual row order, determined empirically

**[V]** `EXPLAIN QUERY PLAN` on the widened (non-`--geo-only`) candidate
query: `SCAN markets` — a full table scan, no index used (neither
`end_date` nor `resolution_date` is indexed). `markets.market_id` is
declared `TEXT PRIMARY KEY`, not `INTEGER PRIMARY KEY`, so it does **not**
alias SQLite's internal `rowid` — the table has its own hidden `rowid`,
and an unordered scan returns rows in **rowid order**, i.e. **insertion
order**, confirmed deterministic across repeated calls and fresh
connections (`SELECT ... LIMIT 500` run twice, byte-identical market_id
lists both times). The first rows returned have `rowid` 9, 10, 23, 44,
45... — among the very earliest rows ever inserted into this table.

### (b) Current failure rate — measured directly against live CLOB, at the actual head of the widened scan

**[V]** Live-tested (real `_fetch_by_clob` calls, this session, no
writes) against the widened query's own first 300 rows by rowid — not
the 317-market Q2 census used in prior steps, which is a *different*
population (Geo/Elections-filtered):

| Rows (by scan position) | Result |
|---|---|
| 1–98 | **100% `no_clob_response`** (HTTP 404 — confirmed by direct `curl`, not inferred from the wrapper) |
| 99–~150 | Dominated by `indeterminate` (CLOB responds but `closed` is missing, or closed with no winner) |
| ~150–300 | Increasingly `resolved` |
| **Aggregate over 300** | resolved=120 (40.0%), indeterminate=82 (27.3%), no_clob_response=98 (32.7%) |

**The 404s are not a sampling artifact of an unlucky small draw — the
first small sample (n=40) was 100% failing, and a full re-test of the
same 300-row window shows the failing rows are concentrated in an exact,
sharp band: rows 1–98 are 100% `no_clob_response`; row 99 onward, zero
further `no_clob_response` appears through row 300.** `curl` against a
market from this band directly: `HTTP 404`. **CLOB genuinely does not
serve markets this old** — sampled titles from this band: *"What will the
total value locked (TVL) in DeFi be at the end of 2020"*, *"Which party
will win North Carolina in the 2020 presidential election"* — Polymarket's
earliest markets, `data_source='historical_backfill'` overwhelmingly (490
of the first 500 rows are `historical_backfill`; only 10 are
`live_monitoring`). These are not missing an identifier (unlike
`hydrate_stub_markets.py`'s trap) — all 500 sampled rows have **both**
`condition_id` and `api_id` populated. CLOB itself has simply purged them.

### (c) Is this reached slowly, or is it already fully realized?

**Already fully realized — not a slow accumulation.** The scan order is
deterministic and the failures are permanent (a 404 for a delisted market
does not become a 200 on retry). Every future daily run, forever, would
re-issue the identical first ~98 calls and get the identical 404s —
**from the very first invocation**, not after N days of accumulation.
This differs from the task's own framing ("reached slowly rather than
immediately") — measured, it is immediate and permanent, not gradual.

**But it is bounded, not total — a materially different severity than
`hydrate_stub_markets.py`'s ~99% failure rate.** At today's actual
scheduled `--limit 500`, the fixed ~98-row dead zone would consume
**~20% of the daily budget**, permanently, while the remaining ~80% (rows
99–500) reaches a real, useful mix — genuine `indeterminate` and
`resolved` outcomes, including actual new discoveries. This is a real,
confirmed, permanent tax — not a total-paralysis trap. Both things are
true and are reported as such, not rounded toward the more dramatic
framing.

### (d) Options to avoid the tax — assessed, not chosen

1. **`ORDER BY` (e.g. rowid descending, or by `last_checked`/recency)** —
   would reprioritize the *newest* candidates first, likely surfacing
   real discoveries faster, but does not eliminate the dead zone — it
   only defers it to whenever the newer population is exhausted. §C's own
   sweep-scoped reasoning ("population shrinks on success, so ordering is
   for legibility, not correctness") does **not** transfer to the daily
   run for exactly the reason this task hypothesized: the daily run never
   exhausts the population, so a permanently-failing subset at any fixed
   scan position is retried forever regardless of which end it sits at.
2. **A permanent skip/exclusion marker** — e.g. a `clob_checked_no_response`
   flag or timestamp, set once a market gets an HTTP 404 (or `no_clob_response`
   generally) and used to exclude it from future candidate scans without
   retry-backoff logic, since these are not transient failures a backoff
   would ever resolve. Likely the most *correct* fix for this specific
   failure mode (permanent, not transient) but is itself a schema/behavior
   change beyond "change the predicate."
3. **Retry-with-backoff on an `attempted_at` timestamp** — the mechanism
   named in the task prompt; would help for *transient* failures but does
   nothing for permanent 404s, which would simply re-enter the retry queue
   on the same fixed cadence forever. Less suited to this specific failure
   mode than option 2.
4. **Do nothing about ordering; raise `--limit` far enough that the fixed
   ~98-row cost becomes proportionally negligible** — e.g. at `--limit
   5,000`, the same ~98-row permanent tax is ~2% of the budget, not ~20%.
   Cheapest option, addresses blocking question 2's arrival-rate gap at
   the same time, but leaves a permanent (if small, and shrinking as a
   fraction) dead cost in every future run indefinitely.

**Not decided here.** All four are real options with different
trade-offs; the task's own instruction is to report, not pick.
