# Session Summary — 2026-08-22 through 2026-08-24

## THEME

The discovery-gap sweep went from pre-registration to ~65,000 markets
resolved in production, through a staged rollout that stopped itself four
times — every stop finding something real, never a false alarm waved
through. The period also included a 6-hour network outage with no data
damage, a log-reading trap that made the first incident report wrong about
where the run actually stalled, and two safety fixes built in direct
response to a survey of what could still go wrong. It ends with segment 3
running and its outcome genuinely unknown at time of writing.

## FIVE REUSABLE LESSONS (record them)

**A threshold that cannot fire is worse than one miscalibrated.** Tranche
1's batch-level condition (10%, evaluated over "the last completed batch")
was structurally inevaluable at tranche 1's own population size — 317 rows
never completes a 500-row batch, so only the cumulative counter was ever a
real guard, and this was true from the moment the pre-registration was
written, not discovered as a bug. A condition's evaluability against the
actual population it will run against must be checked, not assumed from
its threshold value alone. Batch size and population size interact.

**Fix the threshold's structure, never its value, while a run waits on the
answer.** Tranche 1 paused at row 25/317 when 3-of-25 crossed the 10%
threshold. The condition had no minimum sample size; at n=25 against a
known 5.05% baseline, P(X≥3) ≈ 13% — it fired on ordinary variance, not
signal. The fix was an n=100 floor (binomial: P(X≥11) at n=100 ≈ 1.5%),
with the 10%/20% rates themselves left untouched and the batch/cumulative
counters separated. This is a structural correction that would have been
right from the start, not a relaxation chosen because a stop was
inconvenient — raising 10% to 15% would have been the latter. The
distinction is the whole difference between discipline and theatre, and it
recurred in reverse at segment 1: when the same batch-level condition fired
again at n=500 (five times the floor, 13.6%), it was correctly treated as
real signal, not re-litigated as more noise, precisely because the floor
now existed to make that distinction possible.

**A random sample characterizes a population's average, not its shape.**
Tranche 2's seeded 5,000-market sample validated the write path and the
kill-resume guarantee, but it could not have surfaced either dead cohort
this arc found — the ~98-row CLOB-purged prefix (step 2's finding) or the
15,427-row combo/parlay cohort (segment 1's finding) — because a random
draw scatters a 3%-of-population cluster to roughly one per batch,
invisible against a ~3.5–4% baseline. Segment 1's scan-order walk
concentrated the combo/parlay cohort into one contiguous stretch (indices
6,000–23,094) because `market_id` sorts by shared ID *format*
(zero-padded suffix), not by insertion time — the mechanism is precise, not
"old markets cluster together." Validating on a random sample and then
executing in scan order are different exposures to the same population.

**Enumerate the whole return surface, not the case that fired.** Tranche
2's kill test produced 92 `"no-op: same-rank value matches existing"`
results that the driver's whitelist didn't recognize, correctly pausing
the run. The fix that mattered was not patching that one string — it was
reading `monitoring/resolution_writer.py` in full and classifying all nine
possible reason strings by hand. That enumeration caught a second,
unfired gap in the same pass: `"written: proposed evidence outranks
existing"` (the cross-rank overwrite the pre-registration itself calls
"allowed and expected") was also missing from the whitelist. Had it not
been added then, it would have paused the sweep hours into a later,
unattended run on behavior explicitly designed to be normal.

**Verify every claim that reaches a decision document, including the ones
written into the prompt.** Three specific claims were asserted in task
prompts across this period and later found wrong by direct verification,
not inherited: `resolution_sweep.py` framed as a second writer into
`markets` (it only reads `resolved=1` and writes `traders`); "~25
unhardened daily-maintenance scripts" (actually ~5 of ~30, and only two —
`fast_resolution_check.py` and `resolve_legendary_markets.py` — touch
`markets`); and segment 3's own launch prompt sizing the runway from
2026-08-23's maintenance window when 2026-08-24's had already run and
finished hours earlier. Each was caught by checking the code or the clock
directly rather than propagating the premise forward into a decision.

**1. The overnight incident, diagnosed and then corrected.** A ~6-hour
Mullvad/Tailscale network outage began 03:24:13 UTC, ended by an
unexplained reboot at 09:29:56 UTC (`2026-08-22-overnight-incident.md`,
`696b49d`). Verdict: **NO DAMAGE, CAUSE IDENTIFIED** —
`PRAGMA integrity_check` clean, WAL 0 bytes, no write activity during the
window, resources normal throughout (0% swap used every 10-minute sample,
no OOM, `sar` clean). The widened `--limit 35000` backfill step was
cleared: it sits at position 32 of ~29–33 steps and the run never got
close.

A correction found the next session (`2026-08-22-incident-report-correction.md`,
`8293054`) fixed *where* the run actually stalled: not step 5 (Resolution
sweep, as first reported) but step 12 (`backfill_transaction_hashes.py`,
590/3737 processed). Steps 1–11 had completed in full, including
Resolution sweep itself, with real non-zero results (57 markets resolved,
6 traders promoted). Root cause of the misreading: `daily_maintenance.py`'s
parent process buffers its own `--- Step: {label} ---` headers via a plain
`print()`, while each child subprocess's stdout writes straight through
unbuffered. A kill before the parent's buffer flushes loses every parent
header from the log, leaving only child output — a grep for the parent's
own strings then finds nothing past the start marker, producing a false
"stalled early" reading. This will recur every time the box dies mid-run
unless the parent's own output is flushed per-step. The verdict (no
damage) was unchanged and strengthened, not overturned.

**First kill test:** SIGKILL 41 seconds into batch 1, 92 markets already
written (no checkpoint existed yet — batch 1 never completed one). Restart
correctly started fresh. **Zero double-writes**, verified by direct
timestamp inspection (none of the 92 had `resolution_recorded_at` changed

378 (resume's fresh batch-1 writes) = 673, matching the live count.

The run then stopped on abort condition 5 ("unpredicted rejection
pattern") — and what fired proved the comparator works: `"no-op: same-rank
value matches existing"` was not in the driver's whitelist, so 92 benign
re-confirmations counted as unpredicted rejections at 24.3%. A same-rank
*match* is confirmation, not disagreement; the whitelist had conflated
them. The subsequent fix enumerated all nine of `mark_market_resolved()`'s
possible reason strings by hand and found a third, unfired gap in the same
pass: `"written: proposed evidence outranks existing"` — the cross-rank
overwrite the pre-registration itself names as "allowed and expected" —
was also missing, and would have paused a much longer run on entirely
correct behavior. Skip-list predicate widened from `reason == "written"`
to `reason in ACCEPTED_REASONS`. Both fixes verified in both directions
against the real, unmodified `mark_market_resolved()` (not reimplemented)
in an in-memory DB, nine checks, all passed.

**Completed: 10/10 batches, 4,723 markets confirmed resolved
(`resolution_evidence_source='clob'` 673 → 4,926, exact match), zero
aborts.** A second SIGKILL, mid-batch-4 with checkpoints already on disk,
resumed correctly from the persisted checkpoint at the right batch; 264
pre-kill writes verified untouched by direct timestamp inspection, same
method as the first kill. An honest architectural finding surfaced by this
second test, not glossed over: the checkpoint's market-level skip-list is
**structurally unreachable** under this driver's design — non-overlapping,
fixed batch slices and a loop that never re-enters a completed batch mean
`resolved_market_ids` and any batch's own slice are always disjoint sets.
The no-double-write guarantee rests entirely on `mark_market_resolved()`'s
own comparator, now confirmed under SIGKILL twice, not on the skip-list
runtime-checking anything.

**The number that changed the plan:** observed pacing across all ten
clean batches was **0.416s/call**, in a tight ±3% band (202.6s–214.0s per
500-row batch) — 66% above the 0.25s planning assumption, driven by real
CLOB round-trip time on top of the deliberate sleep. The full-sweep
runtime estimate was revised from ~36 hours to ~60 hours on this figure.

**5. The execution model assessment**, prompted directly by that revision
(`2026-08-22-sweep-execution-model.md`, `a972731`; pre-reg amendment
`2e1bb34`). Recommended chunked/scheduled segments over one continuous
detached run — the only model where a human judges the maintenance-window
collision at each segment boundary rather than accepting it (a systemd
auto-restart) or hoping to notice it (a bare continuous run). Two findings
inverted the framing going in: the sweep itself is the *robust* party (30s
`busy_timeout`, short committed-per-row transactions) and daily_maintenance
the fragile one (~5 of ~30 steps run with Python's bare ~5s default,
though only two — `fast_resolution_check.py`,
`resolve_legendary_markets.py` — actually touch `markets`); and
interruption cost is immaterial to the model choice (~208s of re-work per
kill, confirmed empirically by both tranche 2 kill tests, against a run
measured in tens of hours).

**10. The two safety fixes.** (`2026-08-23-sweep-safety-fixes.md`,
`4b3f69e`, code `e4ddb67` and `72e7337`.)

**Fix 1, checkpoint-recency hold** (`e4ddb67`): the daily "Backfill market
dates" step now checks `_sweep_recently_active()` before running, skipping
(not failing) if any `data/checkpoints/segment*_checkpoint.json` was
updated within 1800s — reusing the sweep driver's own
`MAINTENANCE_STOP_MARGIN` constant, ~8.6x the observed ~208s per-batch
cadence. Fail-open at two layers: any single unreadable/malformed
checkpoint is skipped, not raised, inside the scan; and if *no* checkpoint
yields a usable age at all, the function returns `active=False` — the step
runs. A broken checkpoint can never silently disable a daily step
indefinitely; at most it holds one step for up to 30 minutes past when the
sweep actually died. Proven to fail against the pre-fix baseline by
dynamically loading the exact pre-fix file as a live module and hitting
`AttributeError` — the strongest available form of "the test would have
failed before this fix."

**Fix 2, terminal signal** (`72e7337`,
`data/characterizations/sweep_common/sweep_terminal_signal.py`, new file):
`write_terminal_marker()` (atomic, same temp-file-then-`os.replace`
pattern as the checkpoint) and `send_telegram_terminal()` (a synchronous,
fire-and-forget send modeled on `audit_invariants.py`'s already-established
pattern, not the heavier long-lived `TelegramNotifier` class), for a
driver to call at its three exit points. Guaranteed never to raise —
verified by simulating both a successful and a failing send with
`asyncio.run` monkeypatched; no real network call made by the test suite.
Explicitly **not** wired into `segment2_write.py` (that segment had
already completed before the module existed — retrofitting a finished,
committed driver would misstate what code actually produced its results,
a hard line per this arc's own reproducibility discipline). The SIGKILL
limitation stated plainly in the module's own docstring: nothing in
userspace can trap a hard kill, so no marker and no Telegram message is
possible in that case — the absence of *both* a marker and a recent
checkpoint is itself the signal a hard kill leaves behind.
