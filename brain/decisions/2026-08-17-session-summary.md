## TWO REUSABLE LESSONS (record them)

**A red check that cannot distinguish severity is only a prompt to investigate, not a finding.** Daily maintenance step 8 (canonical-definitions drift) failed today exactly as it has for several runs — six sites, one violation type, no severity information. Read literally, that failure looked identical whether the six sites gated the cohort behind the result of record or did nothing but print a diagnostic. Only a manual per-site trace (`2026-08-17-legendary-gate-drift-probe.md`) could tell the two apart, and reading the checker's own source confirmed why: it flags any canonical-shaped SQL threshold string that sits outside a `print`/`log` call, with zero model of what the query's result is later used for. This is the inverse of the standing lesson from earlier work that a green check is a claim, not proof — the same defect showing up on the other side of the ledger. A red check that can't grade its own violations is a todo list, not a verdict.

**Pinning one side of a comparison does not pin the comparison.** `bt_pop_2025-11-01_v1` was confirmed intact — 4,712 rows, one generation event, the only write path an idempotent `INSERT OR IGNORE` — and the predicate it was frozen under (`backtest_window_sql()`) has not changed since, two commits ever, both on freeze day. Reconciliation against it still broke, because the *other* side of the comparison — `markets.category`, `markets.resolution_date` — is mutable and gets silently, progressively backfilled forever. Freezing an artifact against a substrate that keeps moving doesn't remove the comparison's instability, it just relocates where the instability shows up. This is the same shape as the Objective 2 persistence gap found 2026-08-16 (a cohort that was never pinned in the first place): both are cases where "we have a fixed reference point" turned out to mean less than it sounded like, because only one side of the thing being compared was actually fixed.
