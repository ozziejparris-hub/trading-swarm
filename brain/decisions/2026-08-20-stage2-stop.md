## Q1 — the COALESCE divergence

**(a) Does `batch_update_resolved_markets` ever hold a true event-time
from Gamma? — [V], read in full, `scripts/fast_resolution_check.py`
lines 258–275.**

```python
winner = self.extract_winner(market_data)
if winner:
    if not test_mode:
        cursor.execute("""
            UPDATE markets
            SET resolved = 1,
                winning_outcome = ?,
                resolution_date = COALESCE(resolution_date, ?),
                last_checked = ?
            WHERE market_id = ?
        """, (winner, datetime.now(), datetime.now(), market_id))
```

**No.** The `resolution_date` parameter is `datetime.now()` — write-time,
not any field read from `market_data` (Gamma's full response dict, which
does carry `endDate`/`closedTime`-style fields, but this function never
reads them for this purpose). This matches the design's own A2 ranking
table, which already lists writer #3 among the six writers using
`datetime.now()` at write time, not a true event-time source. Under
migration, `resolution_event_time` would always be `None` for this writer
— there is nothing else to supply.

**(b) At-risk population, verified against today's data, not reused —
[V]:**
```sql
SELECT COUNT(*) FROM markets WHERE (resolved = 0 OR resolved IS NULL) AND resolution_date IS NOT NULL;
-- 1349
```
**Exactly 1,349** — identical to the figure the clobber-fix doc cited.
Not assumed unchanged; independently re-queried today.

**(c) Do the two behaviors diverge? — No.** `mark_market_resolved()`'s
three-tier fallback, with `resolution_event_time=None`: use the existing
`resolution_date` if non-null, else write-time. `COALESCE(resolution_date, ?)`
with `? = datetime.now()`: identical — keep existing if non-null, else the
same write-time value. Since this writer never supplies an event-time
(established in (a)), the two mechanisms are behaviorally identical for
every one of the 1,349 at-risk rows. **No divergence.**

## Q2 — `winning_outcome` and `resolved` guards

**Writer's guard, as written:** winner is extracted *before* any DB
action; if `extract_winner()` returns `None`, the function takes **no**
action at all for that market (no write, no counter increment beyond the
implicit loop continuation) — confirmed by reading lines 258–261, there is
no `else` branch. Measured today **[V]**: `winner_none = 0` across all
2,100 Gamma-resolved markets fetched this session — the `has_winner` price
check in `fetch_all_resolved_markets` (same `>=0.99` test) and
`extract_winner`'s own price check agree on every row observed. A
migrated writer that calls `mark_market_resolved()` only inside the
existing `if winner:` block (mirroring the current guard exactly, not
passing `allow_no_winner=True`) reproduces this behavior by construction —
**no divergence for the winner-absent case.**

**The `is_resolved` guard is where Q2 and Q3 are the same finding, not two
separate ones — stated explicitly rather than double-counted:**
`if is_resolved: already_resolved += 1; continue` (line 254–256) is a
**hard, unconditional skip** — the writer never re-touches an
already-resolved row, regardless of evidence quality. `mark_market_resolved()`
does not hard-skip on `prev_resolved == True`; it compares rank, and (per
Stage 0's own documented interpretation) an untagged existing value is
always improvable. The quantification of exactly how often this fires is
Q3, below — Q2 is answered by pointing at it rather than re-deriving the
same number twice.

## Q3 — untagged legacy rows

**Method — read-only, against the live Gamma feed, no writes issued
[V]:** ran `FastResolutionChecker.fetch_all_resolved_markets()` (the
writer's own method, unmodified) and, for every returned market, looked up
the matching DB row via the writer's own lookup query
(`api_id = ? OR market_id = ? OR condition_id = ?`), then classified it
against both the current guard and `mark_market_resolved()`'s comparator
logic — without calling either write path.

**A production-scale constraint surfaced doing this, worth recording:**
Gamma's `/markets` endpoint returns HTTP 422 once `offset` passes 2100 —
confirmed today, and confirmed as a standing condition, not a one-off, by
cross-checking `logs/daily_maintenance.log`'s history of real production
runs: every recent run logs `Resolved markets from API: 2100` exactly.
The function's own comment references a 50,000-market safety cap that is
never reached in practice — the real cap is Gamma's, at 2,100, on every
run. This is **not** one of the four blocking questions and does not
itself block Stage 2, but it means "the writer's candidate population" is
smaller and more stable in practice than the code's own comments imply,
which is directly relevant to how large the divergence below actually is.

**Results, full 2,100-market fetch [V]:**

| Category | Count |
|---|---|
| Total Gamma resolved-with-winner markets fetched | 2,100 |
| `not_found` (no DB match) | 474 |
| `winner_none` (extract_winner failed) | 0 |
| Not yet resolved in DB — old writer's normal write path | 8 |
| **Already `resolved=1`, `resolution_evidence_source IS NULL`, SAME winning_outcome as Gamma's current read** | **1,618** |
| Already `resolved=1`, untagged, DIFFERENT winning_outcome | 0 |

(The last two rows are near-zero because only 1 row in the entire 224,955-row
resolved population is currently tagged at all — Stage 1's single write.
`resolved_untagged_total` DB-wide: 224,954 **[V]**, of which today's
2,100-market Gamma window overlaps 1,618.)

**The divergence, stated precisely:** under a literal migration (drop the
`is_resolved` guard, let `mark_market_resolved()` decide), the first live
run would issue 1,618 accepted writes that the current code issues zero
of. **Every one of those 1,618 writes would set the identical
`resolved`/`winning_outcome`/`resolution_date` values already stored** —
confirmed by the same/different-winner breakdown above, not assumed. What
changes is provenance metadata only: `resolution_evidence_source` goes
from NULL to `'gamma'`, `resolution_recorded_at` goes from NULL to the
write-time of this run. **No incorrect value would be introduced for any
of the 1,618 rows checked.** This matches Stage 0's own documented design
intent verbatim ("an untagged existing value is treated as lower-ranked
than any real, tagged evidence_source, so a canonical-path proposal can
always improve on a legacy, unranked value") — this is not a bug in the
comparator, it is the comparator doing exactly what Stage 0 specified.

**Why this still needs to stop rather than proceed, despite being benign
in this sample:** two reasons.
1. **Volume and unattended execution.** This is 1,618 additional `UPDATE`
   statements (each preceded by its own `SELECT`) on the very first
   migrated run of a script that executes nightly, unattended, as
   `daily_maintenance.py` step 6 (`--stale-limit 500`, no `--limit` on the
   Gamma fetch). Nobody is watching that run. A design decision this size
   — converting a routine "find new resolutions" maintenance step into
   also being a legacy-metadata-backfill pass, silently, on its first
   unattended firing — is the kind of consequential, hard-to-reverse-by-
   accident change the standing instruction's STOP clause exists for, even
   though the specific values involved check out safe.
2. **This sample is not a completeness guarantee.** The 1,618 figure
   covers only the ~2,100 markets in Gamma's current recency window. The
   design's Stage 0 interpretation, once live, would also fire against
   whatever the CLOB-based passes in the same file (`run_stale_clob_pass`,
   `run_recent_overdue_pass`, `run_external_seed_pass` — writers #4/#5/#6,
   explicitly **not** in scope for this task) eventually migrate to
   Stage 3, and against every subsequent stage's writer. Confirming "safe
   today, for this one writer, for this one 2,100-row window" is not the
   same claim as "safe as a general policy for every future
   already-resolved-untagged intersection this arc will encounter" — that
   broader question is exactly what the options below ask Oscar to settle
   once, rather than re-litigating per writer at every stage.

## Q4 — proxy/assertion split

**Does this writer ever write resolution state for a market that is NOT
resolved? — [V], read in full, lines 176–313.** No. Every write is gated
inside `if winner:`, and every market reaching that point already passed
`fetch_all_resolved_markets`'s own `has_winner` filter (`outcomePrices
>= 0.99`). Every accepted write sets `resolved = 1`; there is no branch
that writes `resolved = 0` or fills `resolution_date` as a scheduled-
end-date proxy on an open market. Unlike `hydrate_stub_markets.py`
(Stage 1), this writer is a pure resolution-**assertion** writer with no
second operation hiding inside it. **§A's proxy-writer allowlist does not
need amending for this writer.**

## Options for Oscar

1. **Migrate exactly as specified — drop the `is_resolved` guard, let
   `mark_market_resolved()`'s comparator decide everything.** Matches the
   design's summary-table description for writer #3 and Stage 0's own
   stated intent for untagged rows. Accepts that the first live run
   performs ~1,618 tag-only backfill writes (confirmed value-safe above),
   with near-zero incremental writes on subsequent nightly runs once those
   rows are tagged (they'd hit the same-rank "already matches" no-op
   thereafter). This also implicitly sets the policy for every later
   stage: opportunistic legacy-tag backfill is an accepted, in-scope
   side-effect of any writer migration under this design, not something
   each stage re-decides.
2. **Migrate the genuinely-new-resolution path only; keep the
   `is_resolved` hard-skip guard in the migrated code, ahead of the
   `mark_market_resolved()` call.** Reproduces current behavior exactly —
   the before/after dry-run diff would show zero difference, the same bar
   Stage 1 met. Defers legacy-tag backfill to a separate, dedicated,
   deliberately-run task (not bundled into a nightly unattended step).
   Narrower migration, in the same spirit as Stage 1's own scope.
3. **Hybrid: migrate with the guard removed (option 1's end state), but
   land it by first running the migrated script manually, once, observed
   — the same discipline already used for Stage 1's and this task's own
   verification steps — specifically to absorb the initial 1,618-row
   backfill under supervision, before letting the nightly unattended
   schedule pick it up.** Gets to option 1's end state without the "first
   unattended run does something new and large" exposure named in Q3's
   reason 1.
4. **Defer Stage 2 until the general policy question is settled once,
   for the whole arc, not just this writer** — since every future writer
   migration is structurally likely to encounter its own
   already-resolved-untagged intersection (Stage 3's CLOB passes
   especially, given their `#4/#5/#6` writers also run against markets
   this writer and `resolve_legendary_markets.py` may have already
   touched). Treat "should a migrated writer opportunistically backfill
   evidence tags on rows it wasn't previously responsible for" as a
   design amendment to `2026-08-19-canonical-resolution-write-design.md`,
   answered once, rather than re-derived at Q3 of every subsequent stage's
   stop-or-proceed check.

**No preference stated this time, deliberately** — Stage 1's stop named a
mild preference for the option that kept that migration narrowest; here,
options 1 and 4 both have real structural weight (1 matches the design's
own already-written intent almost exactly; 4 would save re-answering this
same question at Stages 3–6), and naming one over the other would be
picking a behavior rather than reporting the divergence, which is exactly
what this document is instructed not to do.
