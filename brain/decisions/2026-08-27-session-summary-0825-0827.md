# Session Summary — 2026-08-25 through 2026-08-27

## THEME

Two sweep segments ran: segment 3 completed cleanly (186/186 batches,
93,000 markets), segment 4 self-aborted at batch 101/133 (76%) on its
pacing condition. The abort led, through three successive diagnostics —
a pacing analysis, a backup-log cross-reference, and a full backup
investigation — to a cause nobody would have guessed from the sweep
alone: **the nightly database backup and a running sweep segment are
structurally incompatible.** SQLite's Online Backup API restarts its copy
whenever an already-copied source page is modified, so a
continuously-writing segment can starve the backup indefinitely; the
starved backup's I/O contention is what tripped segment 4's pacing
threshold. The period ended not with more sweeping but with a verified
`flock` overlap guard, a launch-time-dependent scheduling rule, a
six-item pre-registration amendment, and a committed test harness — plus
a newly-surfaced 16,000-market gap that segment 5 must close before it
draws anything fresh. No data damage anywhere across the three days.

## FOUR REUSABLE LESSONS (record them)

**A metric that sums two quantities will point at the wrong one.** Abort
condition 7's `avg_pace` is measured from immediately before the CLOB
fetch to immediately after `mark_market_resolved()` + `conn.commit()`, so
it times network latency and the local DB write as a single number. The
driver connection also carries `PRAGMA busy_timeout=30000`, which makes
write-lock contention wait silently rather than raise. The combination
means lock contention and a slow CLOB API produce an identical signal:
gradual slowdown, no exception, no distinguishing log line. Condition 7
fired correctly and stopped the run — and its own label ("pacing") sent
the first read straight at the CLOB. The real cause was only found by a
deliberate diagnostic that reached outside the sweep's own telemetry into
`backup.log` and `sar`. This is the same one-measurement-two-questions
shape this arc has hit before; the fix each time is to split the timer,
not reinterpret the number.

**Rule out the comfortable explanations by evidence before accepting
one.** The pacing diagnostic did not stop at the first plausible story.
Cohort-specificity: ruled out by re-probing the actual slow markets *and*
a fresh control sample hours later — both returned clean and fast.
Duration or volume throttling: ruled out because segments 2 and 3 both
ran longer and larger without the effect. A CLOB-side change: ruled out
by the shape of the curve — a sudden step from 0.239s/call (batches 1–95
median) to ~1.0s/call at batch 96, held flat for the six remaining
batches, not a drift. Only after all three were closed did the
investigation look at what else started at 03:00 UTC. Any of the three
would have been an easy answer to write down.

**A notification that never fires is indistinguishable from nothing being
wrong.** Segment 3's terminal marker wrote correctly with `COMPLETE`
status and full counts (Fix 2's first live exercise), but its Telegram
notification silently did not send. Root cause: `/home/parison/.env_trading`
contains no `export` statements, so sourcing it in a shell — including
`run_daily_maintenance.sh`'s own `source` — never propagates the
credentials to child Python processes. **Daily-maintenance alerting had
therefore been silently dead too**, not just the sweep's. It surfaced
only because the marker path worked and the notification path did not, in
the same run, making the gap visible by contrast. Verifying a
notification means receiving one — not confirming the config looks right.

**A commit message is not a test result.** The `flock` guard shipped
(`9701d77`) with a verification claim that existed only as prose in the
commit message — no harness, no artifact, nothing re-runnable. Doing it
properly on 08-27 took minutes and produced a committed harness with 27
assertions across 5 scenarios, a negative control against the pre-guard
wrapper, and a demonstrated (not asserted) SIGKILL-survival case. The
claim turned out to be true, which is exactly why the gap was easy to
leave: an unverified assertion and a verified one read identically until
someone checks.

### 2026-08-26 / 2026-08-27

**6. The `flock` guard — shipped and verified.** Guard `9701d77`, doc +
harness `24c7f95`.

- `flock -n` on `run_database_backup.sh`, wrapping the whole body. Chosen
  for the **same self-healing reasoning** that chose checkpoint-recency
  for the sweep's maintenance hold: kernel-held, released on any exit
  including SIGKILL/OOM/reboot, no stale-lock state, no post-crash
  cleanup code — unlike a PID file (PID recycling on a long-uptime box)
  or a `pgrep` check (TOCTOU race, defeated by a rename/re-invocation).
- **Blocked runs SKIP** with a log line naming how long the holder has
  been running — **not silent** (standing practice: a deliberate hold
  must say so), **not queued** (a holder can run 24–48h; queueing just
  defers the pileup a night, worse each time), **not alerting** (cron
  Telegram is still broken by the export gap).
- **Consequence recorded explicitly:** because a starved backup can hold
  the lock 35+ hours, the guard means subsequent backups are *skipped,
  not delayed* — correct behaviour, but on its own it could leave several
  nights with no fresh backup. **The scheduling rule (§7) is the primary
  remedy; the guard is the backstop** that stops a collision from
  compounding into a second overlap.
- **Verified properly** on 08-27 after the prior session was cut short by
  a usage limit: a committed harness (`tests/test_backup_overlap_guard.sh`),
  **27 assertions across 5 scenarios, deterministic over 4 runs, exit 0**,
  fully isolated — temp `SWARM` root, stubbed `backup_database.sh`,
  process-group kills; the production DB, log, and lockfile are never
  touched. Scenarios: (A) blocked path skips with the elapsed-time line
  and does not invoke the backup; (B) allow path proceeds; (C) reacquire
  after clean exit; (D) **SIGKILL survival** — holder killed `-9` with no
  SIGTERM and no cleanup hook, lock auto-releases, next run acquires
  (the property that chose `flock` over a PID file, demonstrated not
  asserted); (E) **negative control** — the same blocked scenario against
  the pre-guard wrapper (`9701d77^`), which runs the backup anyway
  despite a held lock, proving the test depends on the guard.
- **First production run `2026-08-27T03:00:01Z`** took the allow path
  cleanly and completed in ~3 minutes. The blocked path has not yet
  fired in production (no segment was running).

**7. The scheduling rule.** In `2026-08-26-backup-guard-and-scheduling.md`
(`24c7f95`), reproduced from amendment `226e01f` §b. Segments must finish
**before the 03:00 UTC backup**, with a stop-by of **02:30:00 UTC** (the
same 1800s margin as the maintenance-stop boundary) and

```
max_batches = floor( (seconds from launch to the next 02:30:00 UTC) / 209.8 )
```

at segment 3's clean 0.4196s/market = 209.8s/batch rate. Worked examples
for the three recorded launch times: **158 / 104 / 94 batches** (17:15,
20:24, 20:59 UTC launches) — all materially smaller than segment 3's 186
or segment 4's planned 133. **Notable finding: a flat ~10-hour segment
does not fit** — a 10h segment needs a launch by 16:30 UTC and every
recorded launch is later. Segment size now depends on launch time.
**NOT YET IMPLEMENTED in any driver.**
